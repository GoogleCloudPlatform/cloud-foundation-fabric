# Reviewing Cloud Foundation Fabric Pull Requests

Maintainer-facing PR review skill for Cloud Foundation Fabric (CFF). This skill focuses strictly on diagnosing an existing pull request or branch diff and delegates all canonical design, convention, and testing criteria to [cff-contributing](../../contributor/cff-contributing/SKILL.md) with zero rule duplication.

## Step 0: Intake and Checkout Safety

1. **Inspect the full PR or diff:** For a GitHub PR, fetch metadata, checks, linked issues, and diff via `gh pr view <n> --json title,body,author,baseRefName,headRefName,labels,files,statusCheckRollup,closingIssuesReferences`, `gh pr checks <n>`, and `gh pr diff <n>`. For a local branch, inspect `git diff master...HEAD` and `git status`.
2. **Stay read-only on remote PRs:** Never run `gh pr checkout`, switch git branches, or modify the maintainer's working tree without asking first. Read remote files with `gh api` or `git show` when full-file context is needed; run local `tools/lint.sh` or `pytest` only when reviewing the currently checked-out branch or when explicitly asked.
3. **Read full files, not just diff hunks:** Inspect the complete modified `.tf`, `.schema.json`, and test files, any linked GitHub issue, and at least one sibling module in the same family before forming judgments.
4. **Check CI signal first:** Inspect `statusCheckRollup` / `gh pr checks` so you do not repeat failures CI already caught. Focus review effort on what automated checks cannot judge — architectural fit, interface ergonomics, subtle runtime bugs, and test inventory intent.

## Step 1: Architectural Triage (Stop Before Nitpicking)

Before reviewing individual lines, decide whether the PR belongs in Fabric at its proposed boundary. Open [design/modules.md](../../contributor/cff-contributing/design/modules.md) only if module scope or binding ownership is in question, and [design/factories.md](../../contributor/cff-contributing/design/factories.md) only if the diff touches factories, schemas, `project-factory`, or `net-vpc-factory`. Verify:

1. **Logical-entity fit:** Reject thin single-resource pass-through wrappers, standalone feature modules (such as central IAM or tag-binding modules), unrelated resource bundles outside `project-factory` / `net-vpc-factory`, and one-off reference architectures that belong in `fast/project-templates/` or `modules/<module>/recipe-*`.
2. **Ownership and resource-management unison:** Reject project-level companion IAM added inside service modules (expose wiring outputs instead), flag target-side vs policy-side binding ownership violations, and verify that shared capabilities across `organization`, `folder`, and `project` move in unison with identical interfaces.
3. **Factory placement and DAG acyclicity:** In `modules/project-factory`, `module.projects` (Pass 1) feeds `module.kms`/`module.service-accounts`, `module.projects-iam` (Pass 2) settles IAM, org policies, and CMEK bindings, and encrypted sub-resources (`module.buckets`, `module.log-buckets`, `module.pubsub`) stay downstream of `module.projects-iam`. Reject changes that break this ordering, introduce Pass 1 -> Pass 2 cycles, or duplicate resource creation across passes, and keep `project-factory` at its two-pass ceiling (do not propose a third pass; redirect to higher-level org/folder patterns or downstream `project_reuse`).
4. **PR cohesion:** Flag unrelated refactors, drive-by formatting churn, or mixed changes that should be split into separate PRs.

When Step 1 fails (wrong module boundary, thin wrapper, or broken factory DAG), the implementation will be redesigned before its line details matter. Lead with the architectural objection and the right destination, and **stop without running Step 3 line-level audits** — burying a fundamental redesign under secondary nits wastes review cycles and invites false positives.

## Step 2: Verify Every Claim Before Commenting

Never file a technical objection from memory or from partial snippets in a PR description:

1. **Verify against released provider docs:** Check the pinned minimum provider version in [default-versions.tf](../../../default-versions.tf) and confirm resource arguments, defaults, `ForceNew` behavior, and `google` vs `google-beta` availability against a **released** provider tag (see [workflow/pr-lifecycle.md](../../contributor/cff-contributing/workflow/pr-lifecycle.md#pre-design-research-commands) for the raw-markdown fetch fallback).
2. **Verify against sibling modules and ADRs:** Cross-check naming, variable shapes, and file layout against golden-path modules (`project`, `compute-vm`, `net-vpc`, `project-factory`, `net-vpc-factory`, `vpc-sc`, plus same-family siblings) and accepted ADRs in [adrs/](../../../adrs/) (on conflict with `Draft`/`Proposed` ADRs, current golden-path code wins).
3. **Verify HCL and runtime semantics:** Check suspected Terraform or OpenTofu edge cases against [conventions/hcl.md](../../contributor/cff-contributing/conventions/hcl.md#terraform-and-opentofu-runtime-traps) and [CURSED_KNOWLEDGE.md](../../../CURSED_KNOWLEDGE.md). Remember that `locals {}` is an unordered DAG (declaration order does not matter), `nullable = false` cannot pair with `default = null`, and bare `test_name:` keys in `tftest.yaml` are valid shorthand for convention-named `<test_name>.tfvars` / `<test_name>.yaml` cases.

## Step 3: Selective Diff-Triggered Audit Routing

Each canonical guide covers one layer of the repository. Reading guides for surfaces the diff does not touch dilutes attention on the actual code and invites false-positive findings (such as asking a non-factory module for `schemas/` or `FACTORIES.md`). Open **only** the 1–2 guides whose trigger appears in the diff, and never cite a guide, script, or rule you did not inspect:

| Diff touches... | Canonical criteria | Reviewer-specific checks on the diff |
| :--- | :--- | :--- |
| New module, scope change, bindings, new IAM/API/setup resources, `data` sources, `local-exec`, or `outputs*.tf` | [design/modules.md](../../contributor/cff-contributing/design/modules.md) | Verify primary outputs tie internal setup (IAM, APIs, service identities) with `depends_on` (check `outputs.tf` even when untouched in the diff) while applying deliberate dependency tiering rather than blind chaining; challenge any `data` source or undocumented `local-exec`; verify target-entity ownership and `organization`/`folder`/`project` unison. |
| `variables*.tf` or caller-facing interface change | [design/interfaces.md](../../contributor/cff-contributing/design/interfaces.md) | Flag 1:1 raw provider mirroring, invalid attributes for a GCP product subtype, redundant booleans/flags or boilerplate wrapper locals, legacy `default = null` + `coalesce(...)` compatibility shims where a clean provider-aligned default + `upgrade-note` fits better, explicit `optional()` defaults that risk provider drift, `any` types, missing enum `validation`, incomplete `var.context` coverage (audit every scope/reference input in the module such as locations, projects, secrets, service accounts, networks, and KMS keys, not only keys touched by the diff, plus `_vars` exclusion), non-canonical `iam*`/`tag_bindings`/secret (`{value, path, wo_version}`) shapes, and breaking changes missing `moved {}` blocks or `**Breaking Changes**` + `upgrade-note`. |
| `factories_config`, `schemas/`, `project-factory`, or `net-vpc-factory` | [design/factories.md](../../contributor/cff-contributing/design/factories.md) | Verify multi-pass placement (`projects` -> `projects-iam` -> encrypted sub-resources) and DAG acyclicity without proposing a third pass; verify `data_defaults` / `data_overrides` / `data_merges` are not plumbed blindly onto high-risk fields; confirm `.schema.json`, `.schema.md`, [tools/duplicate-diff.py](../../../tools/duplicate-diff.py) copies, and [FACTORIES.md](../../../FACTORIES.md) update together. Skip this row for non-factory modules. |
| `fast/` or high-blast-radius module (`project`, `folder`, `organization`, `net-vpc*`, `vpc-sc`, `net-cloud-armor`, `billing-account`, `iam-service-account`) | [design/fast.md](../../contributor/cff-contributing/design/fast.md) | Check stage contract map stability, byte-identical schema copies in [tools/duplicate-diff.py](../../../tools/duplicate-diff.py), standalone stage usability, and 10-character prefix name budgets (`check_names.py`). |
| Internal `.tf` logic (`locals`, `for_each`, `count`, `dynamic`, `validation`, lifecycle blocks) | [conventions/hcl.md](../../contributor/cff-contributing/conventions/hcl.md) | Catch explicit-`null` `try(var.x.y, {})`, `lower()`, and `contains()` crashes in both `locals` and `validation {}` blocks (`try()` returns `null`, not `{}`), silent no-op `count` gated on nested nullable fields, empty-body `dynamic` permadiffs or `== true` instead of `!= null`, OpenTofu breaks (`provider::` functions, mismatched ternary branch types, unguarded nullable collections), `try()` collapsing partially-known `for_each` maps, `create_before_destroy` contagion across map outputs, `ignore_changes` colliding with additive child resources, and `.name` instead of `.id` references. |
| `tests/` or `README.md` `# tftest` examples | [workflow/testing.md](../../contributor/cff-contributing/workflow/testing.md) | Require tests covering new or changed behavior; inspect **every** changed line in `tests/.../*.yaml` inventories (treat unexplained attribute drops, resource count shifts, or surprise diffs as HCL bugs rather than baselines); challenge any `skip-tofu` or `# tftest skip` tag; flag stray `terraform_data` debug resources. |
| `versions.*`, `default-versions.*`, `README.md` tables, `CHANGELOG.md`, or PR metadata | [workflow/pr-lifecycle.md](../../contributor/cff-contributing/workflow/pr-lifecycle.md) | Every module keeps its own `versions.tf` and `versions.tofu` synced verbatim from `default-versions.*` via [tools/versions.py](../../../tools/versions.py) so consumers can compose modules without constraint conflicts — flag divergent per-module version bumps or extra providers (never ask authors to delete per-module `versions.*`); leave `CHANGELOG.md` to release automation; check for stale `tfdoc` tables, leaked PII, Conventional Commits prefixes, missing `**Breaking Changes**`/`upgrade-note`, and expected `on:*` labels. |

## Step 4: Review Output Discipline and Posting Gate

1. **Lead with a clear verdict:** State `Approve`, `Request changes`, or `Comment (architectural discussion needed)` followed by a 1–2 sentence summary of what the PR does and its main risk or readiness.
2. **Separate blocking defects from nits:** Group findings strictly into **Blocking** (architectural fit, correctness/OpenTofu/permadiff bugs, unguarded breaking changes, missing schema/FAST/unison sync, missing or unexplained test diffs, PII leaks) and **Suggestions / Nits** (ergonomics, naming polish, minor cleanup).
3. **Ground every finding in verified evidence:** Cite exact `path:line` from files you read, state why it matters using verified provider docs, sibling modules, or canonical rules, and offer a concrete idiomatic alternative or direct question. Never cite a file or script you did not read, and never invent findings to look thorough — if the PR is clean, say so briefly and recommend approval. Never imitate CI's `Automated PR Review` format or add decorative status tables or emojis.
4. **Blocking Gate — Maintainer Approval Before GitHub Writes:** Present the complete drafted review (verdict, summary, and inline comments) to the maintainer first. **Never** run `gh pr review`, `gh pr comment`, `gh pr edit`, or `gh pr merge` without explicit approval; if running non-interactively, output the drafted review and stop.
