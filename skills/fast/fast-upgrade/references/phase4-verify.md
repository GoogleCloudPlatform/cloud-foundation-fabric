# Phase 4: Verify & handover

> [!IMPORTANT]
> Start every response with the progress block from [SKILL.md](../SKILL.md).
> You never run `terraform apply`, `destroy`, `import` or `state`
> commands. You run `terraform plan` only when the user asks you to.

## Step 10: Static checks

1. **Factory data.** Every YAML file must still validate against its
   schema:

   ```bash
   uv run scripts/fast_upgrade.py check-data <repo> [<data folder> ...]
   ```

   Exit `2` lists INVALID files: fix them with approval, as in Phase 3,
   Step 9. `UNRESOLVED` with `remote schema (not fetched)` is expected,
   because remote schemas are never downloaded.
2. **Formatting.** For each stage folder that changed:

   ```bash
   terraform fmt -check -diff -recursive <stage folder>
   ```

   Upstream code is already formatted, so any diff comes from merges or
   edits. With approval, run `terraform fmt <file>` on the files it lists.
3. **Validation.** For each mapped stage folder:

   ```bash
   terraform -chdir=<stage folder> init -backend=false -upgrade
   terraform -chdir=<stage folder> validate
   ```

   `-upgrade` updates `.terraform.lock.hcl` to the new provider
   constraints (the PROVIDERS section). The lock file change is part of
   the upgrade and the user commits it. FAST stages often read provider
   and tfvars files generated by earlier stages. If `validate` fails
   because such a file is missing, and not because of the upgrade, say so
   and move on: the plan in Step 11 is the real check.

## Step 11: Per-stage plan review (gate per stage)

**Order.** Go by stage number: `0-*`, then `1-*`, `2-*`, `3-*`. Stages
with the same number do not depend on each other, but all of them depend
on the lower numbers. Ask the user where their own stages fit.

For each stage:

1. **Plan.** The user runs this in the stage folder with their usual
   backend and tfvars (or asks you to run it). `<skill>` is this skill's
   folder:

   ```bash
   terraform init -upgrade
   terraform plan -out=upgrade.tfplan
   terraform show -json upgrade.tfplan | uv run <skill>/scripts/plan_review.py
   ```

   `plan_review.py` also reads a file: `plan_review.py plan.json`.
2. **Present** the `changes:` line, then DESTRUCTIVE (with its CRITICAL,
   `why` and `replace paths` lines), UNRECOGNIZED ACTIONS, SENSITIVE
   UPDATES, MOVED, and REMOVED FROM STATE. Quote the VERDICT line
   verbatim.
3. **Act on the verdict:**
   - `no changes`: normal for an upgrade that only touched code, docs or
     defaults. If the upgrade changed this stage's behavior, check that the
     right folder and tfvars were planned.
   - `no deletes or replacements` (exit `0`): go through the updates,
     sensitive ones first. Authoritative IAM removes members that are not
     in the code; organization policy and VPC Service Controls changes are
     security relevant. Tie expected updates to their BREAKING CHANGES or
     UPGRADING NOTES entry.
   - `destructive or unrecognized` (exit `2`): do not go on to apply. For
     each entry, start from its `why` line:

     | `why` | Usually | Fix |
     | --- | --- | --- |
     | `delete_because_no_resource_config`, `delete_because_no_module`, `delete_because_wrong_repetition`, `delete_because_count_index`, `delete_because_each_key` | the resource only changed address | a `moved` block (look in the target's `moved/` folder first), or a `terraform state mv` that the user runs |
     | `delete_because_no_move_target` | a `moved` block points to an address that does not exist | fix the `moved` block |
     | `replace_because_cannot_update` | an attribute that forces replacement changed (see `replace paths`) | look in the CHANGELOG and UPGRADING notes for a setting that keeps the old value; otherwise the user accepts the re-create explicitly |
     | `replace_by_triggers`, `replace_by_request`, `replace_because_tainted` | a replacement that was triggered, requested or forced by a taint | confirm with the user that it is intended |

     Never accept a CRITICAL entry for the user: read its reason to them
     and wait for their explicit decision. Repeat fix, plan and review
     until the verdict is no longer destructive, or the user has accepted
     each remaining entry explicitly.
4. **Apply.** The user runs `terraform apply upgrade.tfplan`, never you.
   Plan the next stage only after this one is applied, because later
   stages read what earlier ones publish.
5. **Clean up.** Delete `upgrade.tfplan`: plan files contain secrets.

## Step 12: Handover

Write a handover report for the user:

- **Versions**: base and target, plus the verbatim first line (with the
  `tools` digest) of the final `plan` run and of every `plan_review.py`
  run, and every VERDICT line.
- **Apply**: the counts (written, merged, deleted, kept), and each resolved
  conflict with a one-line summary of the decision.
- **Changes you made**: factory data, tfvars, module calls, moved blocks,
  vendored modules.
- **Still open**: deletions that were kept, `terraform state` commands
  from the UPGRADING notes, new stages not adopted, customer-only stages
  still to check, stages not yet planned or applied, in apply order.
- **Fork delta**: the `delta.txt` report from Phase 3.
- **Customer report**: run `plan` again on the upgraded branch with
  `--markdown <repo>/.fast-upgrade/report-after.md`,
  `--brief <repo>/.fast-upgrade/report-after-brief.md` and, if your chat
  embeds HTML, `--widget` into your artifact directory. Show the card and
  the brief inline in the handover, as in Phase 2, and link
  `report-after.md` next to the Phase 2 `report.md`; a diff of the two
  shows which findings are closed and which are still open.
- **A commit message**, for example:

  ```text
  chore(fast): upgrade FAST from <base> to <target>

  - take upstream changes (<n> files) and merge <m> conflicts
  - update factory data and tfvars for <breaking changes>
  - add moved blocks for <stages>
  ```

The user reviews, commits, pushes and opens the pull request. Remind them
not to commit `.fast-upgrade/` (reports that name their resources) or plan
files.
