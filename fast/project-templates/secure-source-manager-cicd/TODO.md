## Template design

- [ ] **How this template names the SSM service agent.** Project templates do not call the `project` module, so there is no `service_agents` output to take `service-<number>@gcp-sa-sourcemanager.iam.gserviceaccount.com` from. The factory tfvars does carry `number`, so a `number` variable plus interpolation works and matches how the factory feeds these templates. Alternative is `modules/projects-data-source`, which costs an API read for something we already hold.
- [x] **Two regions, and they are deliberately different.** The instance and its load balancers are in `europe-west4`, because Secure Source Manager runs in eleven regions and only `europe-west2` and `europe-west4` are in Europe. The worker pool stays in `europe-west8`, the primary location for everything else. So the template keeps both variables. `net-lb-proxy-int` defaults `forwarding_rules_config.global_access` to `true`, which is what makes the split work.
- [x] **Two projects.** `dev-build-ssm-0` holds the instance, the repositories, their BYOSAs and the whole load balancer path. `dev-build-pool-0` holds the worker pool and the build identities. One automation service account, `dev-build-ssm-0-rw`, has IAM in both, so the template spans them with a single provider. `iam.disableCrossProjectServiceAccountUsage` is already disabled on `dev-build-ssm-0` for exactly this, since the BYOSAs live there and the builds run next door.
- [ ] **Who places `roles/privateca.auditor` for the build identities.** Still open, and `dev-build-pool-0.yaml` states the blocker precisely: `iam-service-account` takes `iam_project_roles` so this template can make the grant, but something has to give `dev-build-ssm-0-rw` the right to set IAM policy on `dev-sec-core` first. Stage 0 already delegates the two privateca roles to the project factory, so the cheapest answer is probably the factory rather than here.
- [ ] **What the access path needs in a Shared VPC service project.** Unchanged and still to be discovered by building it, though the surface shrank with the load balancers: two forwarding rules and two addresses on `europe-west4/gce`, rather than NEGs, backend services and a proxy-only subnet. `dev-build-ssm-0.yaml` flags its own `service_agent_iam` as copied from `dev-build-pool-0` and guessed, and its `network_users` as deliberately too wide — the whole VPC rather than the subnets actually touched — to be narrowed to `network_subnet_users` once we know.
- [x] **The pool reaches the VPC by PSC, not PSA.** House convention, and it removes more than it adds. The workers hold an interface in `europe-west8/na` through the `cloudbuild-ew8` network attachment, so they resolve against the VPC's own resolver and the whole peered-DNS-domain mechanism is moot; `route_all_traffic` puts their public egress through `nat-ew8`. The `psa-build` range at `10.8.200.0/24` is gone and the address is free. Range chosen as 200 + region index, keeping the 200 block meaning "producer connectivity" alongside `gce` at 0 and `gke` at 100.
- [x] **No load balancers, for now.** The instance publishes two service attachments and controls only `psc_allowed_projects`; endpoints are the consumer's business and any number may attach. One endpoint per attachment with `global_access` covers every client that shares the VPC, which after the PSC change includes the build workers. An endpoint is unreachable across a peering, VPN or Interconnect, so hub and on-premises clients would each need their own endpoint and their own same-named zone — at which point the `net-lb-proxy-int` pair from Google's guide comes back as the fallback, documented in README under the access path. The switch costs two module blocks and a DNS record, which is why it is worth starting without it.
- [ ] **Whether `psc_allowed_projects` is mutable.** The provider schema does not expose `ForceNew` and everything else on an instance is immutable. If it turns out immutable the list has to be right on the first apply, which changes how the hub gets admitted later.
- [x] **How the template receives the network, the CA pool and the second project.** Logical names throughout, with a static local context supplying the concrete values in the example. That covers the VPC self link, the subnets, the CA pool and the second project's ids uniformly, and means no stage tfvars need symlinking for the example to work.
- [x] **Custom hostnames under `ssm.gcp.qix.it`.** `api.`, `git.`, `ssh.` and the apex for `html`. Chosen over the generated names under `europe-west4.p.sourcemanager.dev` because those embed the instance id and project number and so change on any rebuild, while these survive one and take the region out of the DNS suffix. All four are required by the API and immutable like the rest of the instance. Module support added in `b4467f49e`, along with a `host_config` output.
- [x] **`context` in `modules/secure-source-manager-instance`, now load-bearing.** Settled the same way: the module resolves, and the template will carry a `context` variable of its own with the entries specified statically. The template's `main.tf` still passes plain strings, so wiring the two together is the next step.
