## Module changes to tackle first

The gaps found on 2026-09-12 that sit below the template. Reviewed again on 2026-09-13 and only one is left here; the two that turned out not to block anything moved to the follow-up section at the bottom.

- [ ] **Private Service Connect pools are gated, so the network design is blocked.** Found 2026-09-13 by probing the API directly: a well-formed `v1` create carrying only `privateServiceConnect` returns `400 INVALID_ARGUMENT: Private Service Connect feature is unavailable`. The field is documented in the `v1` discovery document and is not a second generation feature, so this is an allowlist on the project or the organisation and nothing else. Terraform and gcloud both hide it, each omitting the required `publicIpAddressDisabled` so that the API discards the block and creates a networkless pool successfully; Terraform then wants to replace that pool on every subsequent plan. Decide between asking for enrollment and reverting to a peered-network pool, which un-frees the `psa-build` range and makes `peered_domains` load-bearing again. Evidence and consequences in SSM-CB.md.
- [x] **`compute.vmExternalIpAccess` is not a backstop for worker public IPs.** Closed 2026-09-13, against what this file claimed earlier the same day. The workers run in a Google-managed tenant project in Google's organisation, so our organisation policies have no reach over them, and a pool with `PUBLIC_EGRESS` was created here without complaint. The no-external-IP requirement rests on the pool's configuration alone.
- [ ] **Whether the workers really route through the VPC.** Reframed 2026-09-13, and untestable until the PSC gate above is lifted. Attribution to our perimeter is a requirement of the regulated environment this design is for, not a property to note after the fact. `route_all_traffic` names an intent, the workers sit in a Google-managed tenant network that may keep its own default route, and if it does then API calls leave outside our perimeter with no symptom anywhere we look. Test it as attribution, not as routing: have a build step call an API the perimeter denies and confirm the violation lands in our perimeter's audit logs with the worker as the source. Do it on a pool brought up on its own, before the instance, since the pool is cheap and mutable and the instance is an hour and immutable.
- [ ] **`branch_rules` sits out of alphabetical order** inside the `repositories` object. Not enforced (only top-level variables are), left alone. Tidy while in the file for the item above.

## Template design

- [ ] **How this template names the SSM service agent.** Project templates do not call the `project` module, so there is no `service_agents` output to take `service-<number>@gcp-sa-sourcemanager.iam.gserviceaccount.com` from. The factory tfvars does carry `number`, so a `number` variable plus interpolation works and matches how the factory feeds these templates. Alternative is `modules/projects-data-source`, which costs an API read for something we already hold.
- [x] **Two regions, and they are deliberately different.** The instance and its load balancers are in `europe-west4`, because Secure Source Manager runs in eleven regions and only `europe-west2` and `europe-west4` are in Europe. The worker pool stays in `europe-west8`, the primary location for everything else. So the template keeps both variables. `net-lb-proxy-int` defaults `forwarding_rules_config.global_access` to `true`, which is what makes the split work.
- [x] **Two projects.** `dev-build-ssm-0` holds the instance, the repositories, their BYOSAs and the whole load balancer path. `dev-build-pool-0` holds the worker pool and the build identities. One automation service account, `dev-build-ssm-0-rw`, has IAM in both, so the template spans them with a single provider. `iam.disableCrossProjectServiceAccountUsage` is already disabled on `dev-build-ssm-0` for exactly this, since the BYOSAs live there and the builds run next door.
- [x] **Who places `roles/privateca.auditor` for the build identities.** This template does, through `iam_project_roles` on `build-sa`, and a delegated, conditioned `roles/resourcemanager.projectIamAdmin` on `dev-sec-core` names `dev-build-ssm-0-rw` and allows only that role. The alternative, granting from the project factory, cannot work: the factory would be binding service accounts this template has not created yet. Settled 2026-09-12; the delegation itself still has to be written in the security project's data.
- [x] **Who places `roles/iam.serviceAccountTokenCreator` on the Terraform service accounts.** Found and settled 2026-09-12. The last row of the IAM table in SSM-CB.md: each build identity impersonates the Terraform account of the stage it runs, and those accounts live in `iac-0` under stage 0. The sketch placed the grant from `build-sa.iam_sa_roles`, which `dev-build-ssm-0-rw` has no right to do. Two things resolve it. This setup mainly serves application pipelines, whose Terraform accounts this template or the project factory owns, so the row is placeable for them. For FAST stages the build identities go into stage 0 as static context entries in `defaults.yaml`, referenced by `$iam_principals:` in the `iac-0` project's IAM; stages are few, do not grow, and each is brought onto the pipeline only after it has been applied by hand and proven. Not needed for the end to end validation, so `build-sa.iam_sa_roles` stays for the application case and the stage case waits.
- [ ] **What the access path needs in a Shared VPC service project.** Unchanged and still to be discovered by building it, though the surface shrank with the load balancers: two forwarding rules and two addresses on `europe-west4/gce`, rather than NEGs, backend services and a proxy-only subnet. `dev-build-ssm-0.yaml` flags its own `service_agent_iam` as copied from `dev-build-pool-0` and guessed, and its `network_users` as deliberately too wide — the whole VPC rather than the subnets actually touched — to be narrowed to `network_subnet_users` once we know.
- [x] **The pool reaches the VPC by PSC, not PSA.** House convention, and it removes more than it adds. The workers hold an interface in `europe-west8/na` through the `cloudbuild-ew8` network attachment, so they resolve against the VPC's own resolver and the whole peered-DNS-domain mechanism is moot; `route_all_traffic` puts their public egress through `nat-ew8`. The `psa-build` range at `10.8.200.0/24` is gone and the address is free. Range chosen as 200 + region index, keeping the 200 block meaning "producer connectivity" alongside `gce` at 0 and `gke` at 100.
- [x] **No load balancers, for now.** The instance publishes two service attachments and controls only `psc_allowed_projects`; endpoints are the consumer's business and any number may attach. One endpoint per attachment with `global_access` covers every client that shares the VPC, which after the PSC change includes the build workers. An endpoint is unreachable across a peering, VPN or Interconnect, so hub and on-premises clients would each need their own endpoint and their own same-named zone — at which point the `net-lb-proxy-int` pair from Google's guide comes back as the fallback, documented in README under the access path. The switch costs two module blocks and a DNS record, which is why it is worth starting without it.
- [x] **Whether `psc_allowed_projects` is mutable.** It is not. `Instance.yaml` in Magic Modules carries `immutable: true` at resource level, so every field is `ForceNew` in the provider, and the API has no `patch` method, which SSM-CB.md already recorded one section away. The list has to be right on the first apply. The consequence is larger than it looks: today's humans are on the hub, an endpoint does not cross a peering, so the first person to open the web interface from a workstation needs a hub endpoint, and that needs the hub host project in the list at creation. Allowing a project costs nothing, since it only permits endpoints, so the list should carry every VPC host project in the organisation. In the playground that is `ldj-prod-net-landing-0` (hub), `ldj-prod-net-spoke-0` and `ldj-dr-net-spoke-0`; `ldj-dev-net-spoke-0` is the instance's own Shared VPC host and is not the instance project, so it goes on the list too. Closed 2026-09-12, list recorded in `dev-build-ssm-0.yaml`.
- [x] **How the template receives the network, the CA pool and the second project.** Logical names throughout, with a static local context supplying the concrete values in the example. That covers the VPC self link, the subnets, the CA pool and the second project's ids uniformly, and means no stage tfvars need symlinking for the example to work.
- [x] **Custom hostnames under `ssm.gcp.qix.it`.** `api.`, `git.`, `ssh.` and the apex for `html`. Chosen over the generated names under `europe-west4.p.sourcemanager.dev` because those embed the instance id and project number and so change on any rebuild, while these survive one and take the region out of the DNS suffix. All four are required by the API and immutable like the rest of the instance. Module support added in `b4467f49e`, along with a `host_config` output.
- [x] **`context` in `modules/secure-source-manager-instance`, now load-bearing.** Settled the same way: the module resolves, and the template will carry a `context` variable of its own with the entries specified statically. The template's `main.tf` still passes plain strings, so wiring the two together is the next step.

- [x] **The network attachment is applied.** Networking applied 2026-09-13. `projects/ldj-dev-net-spoke-0/regions/europe-west8/networkAttachments/cloudbuild-ew8`, connection preference `ACCEPT_AUTOMATIC`, on subnet `europe-west8/na` at `10.8.208.0/24`. That self link is what the pool's `private_service_connect.network_attachment` takes. The `psa_configs` block it replaced is gone and the `10.8.200.0/24` range is free.
- [x] **The CA pool exists.** `projects/ldj-dev-sec-core/locations/europe-west8/caPools/dev-ca-0`, with CA `dev-ca-0-0`. It is in `europe-west8` while the instance is in `europe-west4`, which is fine — the pool's project and location are independent of the instance's.
- [x] **`peered_domains` is moot.** It only ever existed because a PSA worker sat on the producer side of a peering and could not see the VPC's private zones. On a network attachment it can, so nothing has to be forwarded and the decision about which suffixes to list never has to be made.
- [x] **`dev-build-pool-0` is up.** The missing tfvars file under `projects/tfvars/` was the wrong signal — the project exists, and a template only gets a factory tfvars file when it needs an automation seat of its own. This template does not need one for the pool project: its ids go in as static variable or context values, the same way the network, the CA pool and the second project already do. Closed 2026-09-13.
- [x] **How the hostnames resolve.** Found and settled 2026-09-12. The landing VPC holds centralised DNS and the spokes peer to it, so network-wide records go in the hub; the spokes' environment zones are seen by the hub too. An endpoint address is not network-wide, so neither home fits: hub clients would resolve to an address they cannot reach and time out. With endpoints the answer is a response policy, four local-data rules in `2-networking/dns/response-policies` bound to `$networks:dev` only. It overrides every zone for exactly that network, needs no zone for a domain the landing zone does not serve, and a hub endpoint later means rules in the hub's own policy. The rules must be removed if the load balancer fallback is taken, since the forwarding rule address is network-wide and then belongs in a hub zone that the policy would otherwise override. Reasoning in README under the DNS section.

## Behaviour to verify against real infrastructure

From SSM-CB.md's test list. Order settled 2026-09-13: the pool goes up first, on its own, before the instance. It is cheap and mutable, the instance is an hour and immutable, and three of the things this setup has to prove need only a worker — perimeter attribution, network connectivity and egress through the attachment, and DNS resolution against the VPC's resolver. Endpoint reachability is the one worker-side test that has to wait, since no endpoint exists until the instance does.

Then build the instance and run the two design-invalidating trigger tests against it immediately, before the rest of the template exists.

## Follow-up work, once this project is complete

Out of scope here. Kept because the reasoning is worth not re-deriving.

- [ ] **IAM conditions on the SSM module.** `variables-iam.tf` has no `condition` on `iam_bindings` or `iam_bindings_additive`, and all three IAM variables carry the same description, `"IAM bindings."`. `Instance.yaml` declares an `iam_policy` block and Magic Modules generates conditional support for those by default, so this is module surface rather than provider lag. It is worth fixing because Fabric's standard interfaces are a promise to callers, not because anything here waits on it — see the closed item above for why this design needs none of it, and note that a condition buys little on these two resources anyway, since a repository binding is already scoped to one repository and what remains is `request.time` expiry and `resource.name` matching on the instance. A module change with no connection to this template, so it does not belong on `ludo/ssm-cb`.
- [ ] **Required status checks and code owner approval on branch rules.** Checked 2026-09-12: the REST resource `projects.locations.repositories.branchRules` has `requiredStatusChecks[]`, a list of `{context: string}`, and `requireCodeOwnerApproval`. `BranchRule.yaml` in Magic Modules has neither. Provider lag, not a design problem, and the two fields matter to the design: the status check is the merge gate and code owner approval is what gives CODEOWNERS the weight the second boundary assigns it. Contributing to Magic Modules is outside this template's scope, and Magic Modules is in a frozen period besides, so this waits: contribute both upstream, then add `required_status_checks` and `require_code_owner_approval` to `branch_rules` in the module. Meanwhile the two settings are made in the web interface and the README has to say so.
